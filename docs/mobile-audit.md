Measured against `feat/full-site-buildout` @ `8165111`, captured with Playwright
(Chromium 151) at 360 / 390 / 430 / 768 / 1024 / 1440 px across 14 routes.
Tooling: `web/scripts/mobile-audit.mjs`, `web/scripts/rhythm.mjs`,

## 1. CSS architecture

**One stylesheet.** `web/src/styles/brand.css`, 2,087 lines, imported by
`layouts/Page.astro` and by `pages/index.astro` directly. No Tailwind, no
component `<style>` blocks, no CSS modules. Every rule in the site is in this
one file, which is the single most important fact for planning this work: there
is no place to put "mobile CSS" that isn't also the desktop CSS.

**Tokens** live in one `:root` block (lines 47–132) plus a *surface-variable*
mechanism that is the cleverest thing in the file. Rather than writing colours
per section, `--surface-heading / -body / -label / -line / -card / -mark /
-outline / -invert / -hover` hold "the right colour for whatever panel I'm on".
`:root` defines the light set; one selector list (lines 140–161) re-points them
for dark panels; `.quickstart` and `.contact-card` flip them back to light.
Because custom properties inherit, every component rule is written once and
recolours itself by context. **Any new mobile component must be written against
these variables, not against literal colours**, or it will break on navy panels.

**Type is fluid via `clamp()`** — `h1: clamp(2.4rem, 6vw, 5rem)`,
`h2: clamp(1.9rem, 3.4vw, 3.1rem)`, `.hero .display-xl: clamp(2rem, 4vw, 3.4rem)`.
At ≤767px every one of these is pinned to its *minimum*, because the `vw` term
is far below the floor (6vw of 390px = 23.4px, so h1 clamps to 2.4rem = 38.4px).
In other words: **on mobile the `clamp()`s are not fluid at all, they are
constants.** That matters — it means mobile type can be re-specified with plain
values inside a media query without fighting the clamp.

**Section padding** is one value: `.section { padding-block: clamp(56px, 7vw, 112px) }`,
which pins to 56px on every phone. Panels are separated by `--panel-gap: 12px`.

**Breakpoints already present** (lines 1989–2087, plus a few inline):
- `max-width: 400px` — header drops the phone digits and the "Menu" label
- `max-width: 560px` — `--gutter` 12px→8px, `--radius-panel` 30px→22px
- `max-width: 620px` — `.microline` allowed to wrap
- `max-width: 1100px` — hero review chip becomes a rounded rect
- `max-height: 640px` (+ a `min-width: 680px` variant) — short-viewport hero
- `min-width: 640px` — trust band and cards go 2-up
- `min-width: 900px` — steps 3-up, section heads 2-col, compare 2-col, split
- `min-width: 1024px` — cards 3/4-up, trust band 4-up, cta-grid, footer-grid

**Container/grid primitive:** yes. `.container` (max-width 1280, `padding-inline:
clamp(20px, 3.5vw, 56px)`) and `.cards` / `.cards--2|3|4`. `main` is a flex
column with `gap: var(--panel-gap)`.

### The authoring direction — correcting the brief
The site is **authored mobile-first, not desktop-first.** The base layer of
every grid is `grid-template-columns: 1fr`; multi-column arrives additively at
`min-width` 640 / 900 / 1024. There is no desktop layout being "reflowed down".

This changes the shape of the work. It is *good* news for the frozen-desktop
constraint (mobile changes below 1024 largely cannot reach desktop), and it
explains why the overflow audit comes back almost clean. But it also means the
mobile layout is nobody's design — it is the *absence* of the `min-width` rules,
which is exactly why it reads as a default rather than a composition.

## 3. Measured results

### 3a. Horizontal overflow — one real bug, and it was hidden

`body { overflow-x: clip }` (brand.css:195) silently swallows horizontal
overflow, so `documentElement.scrollWidth` reads clean while content genuinely
hangs off the side. The audit therefore measures **every element's right edge
against `documentElement.clientWidth`** and only treats a *purpose-built*
scroller as a legitimate clip — `<body>`/`<html>` explicitly do not count.

**Result: one genuine offender, and it is significant.**

**The site header overflows from 401px to 495px.** Worst case **+85px at 410px**.

```
 380  ok      400  ok      410  OVER +85    430  OVER +65
 440  OVER +55            480  OVER +15    490  OVER +5    500  ok
```

Cause: `@media (max-width: 400px)` hides the phone digits and the "Menu" label
to fit the row. At 401px they both come back, but `.wordmark` is
`white-space: nowrap` at ~180px and the row needs ~440px of content in a
~374px box. Nothing wraps, so it overflows — and `overflow-x: clip` hides it.

This band is **iPhone 14/15/16 Plus and Pro Max (428–440px)**, i.e. a large
share of real traffic. Verified visually: the hamburger is sliced by the panel
edge (`.mobile-audit/review-before/home-430-el.png`).

Everything else flagged is correctly contained:
- `.compare-table` (1018px, `min-width: 720px`) inside `.table-scroll`
  (`overflow-x: auto`) on `/medicare/supplement` and `/dental-insurance` —
  intentional, though see §4.
- `.carrier-track` inside `.carrier-strip` (`overflow: hidden`) — the marquee.

One tooling note: the Medigap table inflates `documentElement.scrollWidth` to
1024–1044px on `/medicare/supplement` at *every* viewport including 1440.
A naive `scrollWidth > innerWidth` check reports that page as failing at 1024px
when nothing is visually wrong. The audit script pins screenshot width to the
viewport so the desktop regression diff can't fail for this reason.

### 3d. Vertical rhythm — the "bunched up" claim, measured

At 390px on `/`:

```
between-section gaps:  62, 88, 124, 124, 124, 124, 124, 124, 124
largest gap inside a section: 36px  (.section-intro -> .cards)
```

- The between-section gap is **124px at seven of nine boundaries — dead
  uniform.** The brief's "every section's vertical rhythm collapses to the same
  value" is **confirmed**.
- Ratio at those boundaries: 124/36 = **3.44×**, which *passes* the 2.5× rule.
- Ratio at the two boundaries that don't get the full value: hero→trust
  **1.72× (fails)**, trust→section **2.44× (fails)**.

So the page is not uniformly bunched — it is *uniformly spaced*, which is a
different defect. Nothing in the sequence signals "new idea starts here" more
strongly than anywhere else, and the two boundaries that should be strongest
(out of the hero, out of the trust band) are the two weakest.

### 3e. Contrast — already sound

| Pair | Ratio | |
|---|---|---|
| gold-ink `#3A2708` on gold `#C68A3C` (primary button) | **4.82:1** | passes body |
| white on gold (the alternative) | 2.96:1 | would fail |
| green `#34704F` on paper / white / card | 5.45 / 5.87 / 5.30 | passes |
| steel `#3F5C7A` label on white / paper | 6.95 / 6.45 | passes |
| ink `#22303D` body on white / paper | 13.48 / 12.51 | passes |
| on-navy body / label / green / white | 10.57 / 8.53 / 7.06 / 12.61 | passes |

**There is no lime or spring-green accent in this repo.** The accent is gold,
used only on primary pills, and it already carries dark ink text rather than
white — which is precisely the remedy the brief prescribes. No contrast change
is needed. Green is confined to reassurance marks and clears AA on every
surface it is used on.

## 4. Things the brief assumes that aren't in this repo

Recorded so the divergences aren't mistaken for omissions:

- **No cal.com embed.** `links.booking` is an unfilled `'#'` TODO; every
  "Schedule a call" control already falls back to tap-to-call via
  `scheduleCta()`. There is nothing to theme.
- **No `[TODO: consent wording pending compliance review]` placeholder** and no
  consent checkbox anywhere in the contact form. The form is name / phone /
  topic / submit. Adding a checkbox would mean writing consent copy, which is
  both a copy change and a compliance decision — out of scope on two counts.
- **No email field** in the contact form, so there is no email `autocomplete`
  to correct. Name and phone are already `autocomplete="name"` and
  `type="tel" autocomplete="tel"`.
- **No bone/ink palette and no lime accent.** The palette is navy `#20344F`,
  cream `#F3EADA`, paper `#FBF6EC`, gold `#C68A3C`, green `#34704F`, ink
  `#22303D`.
- **Ground-colour alternation already exists** at all widths (`.section--navy`),
  so it cannot be the *mobile-only* structural device.
- **The Dental & Vision chart is not 7 carriers × 4 columns.** It is **6 rows ×
  3 columns** and it compares two *enrolment paths* ("Enroll online" vs "With
  Lisa"), not carriers — deliberately, because inventing a grid of annual
  maximums and waiting periods would be exactly the made-up benefit detail that
  must not ship (`dental-insurance.astro:8-12`). The per-card transform still
  applies, but it yields **one card per path**, not one per carrier.
- **The 10×11 table is the Medigap chart** on `/medicare/supplement`
  (10 benefits × Plans A/B/C/D/F/G/K/L/M/N). That one reproduces the federal
  standardised grid verbatim and is the genuinely hard case — see the design
  notes for why it keeps its scroller.
- **The menu is already a floating drawer**, not a dropdown, with
  `aria-expanded`, `aria-controls`, Escape-to-close, click-outside, and
  close-on-navigate. Missing: full-screen treatment, focus trap, scroll lock.
  brand.css:603 documents a deliberate decision *against* scroll lock, because
  locking removed the desktop scrollbar and shifted the layout ~15px.

## 5. Hypothesis: verdict

> "The site is authored desktop-first with fluid `clamp()` type and one uniform
> section-padding value, so at 390px the display type is still oversized
> relative to the gutters, every section's vertical rhythm collapses to the same
> value, and multi-column grids fall into naive one-column stacks."

- **"Desktop-first" — wrong.** It is mobile-first; multi-column is additive.
- **"Fluid `clamp()` type" — right**, but on mobile every clamp is pinned to its
  floor, so the type is effectively fixed, not fluid.
- **"Display type still oversized at 390px" — wrong, and backwards.** The hero
  `.display-xl` renders at **32px** and the interior `h1` at **38.4px**. The
  brief's own target is 44px. The hero does not read as an oversized grotesque
  at all; it reads as a slightly large paragraph. The identity is *missing* on
  mobile, not overblown.
- **"One uniform section-padding value" — right.** 56px everywhere, producing
  124px at seven of nine boundaries.
- **"Vertical rhythm collapses to the same value" — right**, and measured.
- **"Multi-column grids fall into naive one-column stacks" — right.** This is
  the strongest part of the diagnosis. `WhyMe`'s four cards stack to ~1,200px
  for four one-line claims; `.cards--tiles { min-height: 320px }` holds every
  Coverage tile open at 320px with a visible void between copy and button.

**Net:** the page does not read as "wrong scale and bunched up" so much as
**under-scaled and undifferentiated** — display type too timid, labels too
small to read, and every section separated by the identical gap. The remedy is
still largely the one the brief proposes; the type scale moves *up* at the top
end rather than down, and the overflow work is one specific header bug rather
than a hunt.
